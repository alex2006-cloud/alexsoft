# ADR-0019: Личный кабинет — Next.js SSR (BFF), лендинг — статика, вход через Authentik, JWT проверяет FastAPI

- **Статус:** accepted
- **Дата:** 2026-10-07
- **Контекст:** Нужны три вещи: публичный лендинг для любых посетителей; личный кабинет, где пользователь запускает продукты (AI-агентов из БК1); админ-панель для владельца. В [ADR-0015](0015-target-architecture-stacks.md) Frontend был одним блоком «Next.js», а Nginx значился узлом «OIDC / проверка JWT». Нужно уточнить: как делится фронтенд, где живёт клиент OIDC и кто проверяет JWT. Решение владельца: **архитектура первична**, Authentik и кабинет внедряются **локально сейчас**, не дожидаясь VPS. Схема draw.io (`architecture-in-drawio.drawio`) уже нарисована в этом виде.
- **Рассмотренные альтернативы:**
  - **Весь фронтенд — статика (`output: "export"`), кабинет как клиентские страницы (SPA).** Вход по OIDC с PKCE прямо в браузере, JWT хранится в браузере и уходит в API. Плюсы: нет серверного процесса, деплой как у лендинга. Минусы: токены доступны JS (выше риск при XSS), страницы кабинета не защищены на сервере (защищены только данные в API), внутренние адреса API видны браузеру. Допустим как быстрый MVP; не выбран как целевой. Переезд на SSR позже недорогой, потому что FastAPI и Authentik не меняются.
  - **Один Next.js с SSR на всё (лендинг тоже).** Теряем простой деплой лендинга (rsync статики) и тратим RAM на Node под страницы, которым сервер не нужен. Не выбран.
  - **Проверка JWT на Nginx.** У открытого Nginx нет встроенной проверки JWT (она есть в Nginx Plus). Реальные пути: `auth_request` к Authentik или njs/Lua. Дублирует проверку, которая всё равно нужна в FastAPI (роли и ACL знает только он). Не выбрано как обязательное; можно добавить позже `auth_request` как ранний отсев без смены остальной архитектуры.
  - **Другой IAM** (Authelia, Casdoor, Keycloak). Authelia — слой forward-auth перед прокси, не полноценный IdP; Casdoor в проекте формально не сравнивался; Keycloak и Auth0 отклонены в ADR-0015. Владелец подтвердил **Authentik** (2026-10-07).
- **Решение:**
  ### Frontend — два приложения
  | Приложение | Режим | Деплой |
  |---|---|---|
  | `apps/landing`, `apps/games` | статика (SSG, `output: "export"`), как сейчас ([ADR-0010](0010-games-static-app.md)) | готовые файлы, раздаёт **Nginx** |
  | `apps/cabinet` (новое) | **Next.js SSR (Node) + BFF** | серверный процесс за Nginx |

  Кабинет — один для обоих: пользователь видит свои продукты и агентов, администратор дополнительно — раздел «Админ-панель». Различие задаёт роль, отдельное приложение под админку не нужно. Чат и статус запуска агента (SSE) — клиентский JS внутри страниц кабинета; оболочка, проверка входа и данные первой отрисовки — на сервере.

  ### Маршруты Nginx
  ```text
  /, /games/*, /portfolio/*   → статические файлы (без Node)
  /app/* (включая /app/api/*) → кабинет (Next.js SSR)
  вход (страница Authentik)   → reverse proxy на Authentik (путь или поддомен уточняется при внедрении)
  ```
  Кабинет — BFF: браузер ходит только в кабинет, а он по HTTPS REST (+ SSE) ходит в FastAPI. FastAPI наружу напрямую не публикуется.

  ### Вход и токены
  - Authentik — единственный IdP (OIDC). Кабинет — OIDC-клиент: **Authorization Code (+PKCE) обменивается на сервере кабинета**, токены остаются на сервере, в браузер уходит cookie сессии (`httpOnly`, `Secure`, `SameSite`). Библиотека (Auth.js или `openid-client`) выбирается при реализации.
  - Кабинет передаёт в FastAPI JWT пользователя (`Authorization: Bearer`).
  - **FastAPI проверяет подпись JWT по JWKS Authentik**, claims и роли. **Nginx JWT не проверяет.**

  ### Роли
  | Роль | Источник | Доступ |
  |---|---|---|
  | anonymous | нет сессии | лендинг, портфолио, игры |
  | `user` | группа Authentik `alexsoft-users` | кабинет, доступные агенты, свой Q&A и история |
  | `admin` | группа Authentik `alexsoft-admins` | всё `user` + админ-панель (каталог агентов, коллекции RAG, пользователи через Authentik, ссылки на Grafana / Metabase) |

  Группы приходят в JWT (claim `groups`); FastAPI сопоставляет их с ролями и проверяет ACL на ресурс (агент, коллекция RAG). Тяжёлые админ-UI (Authentik Admin, Grafana, Metabase) не переписываем, на них только ссылки.

  ### Локальная среда (сейчас)
  - **Authentik** не имеет нативной поставки под Windows: запуск через **Docker Compose** в `infra/authentik` — осознанное исключение из правила «на ноутбуке нативно», по прецеденту Dify (`infra/dify`, [ADR-0015](0015-target-architecture-stacks.md)). Требуется запущенный Docker Desktop.
  - Порты: Authentik **9100** (HTTP) / **9143** (порт 9000 занят MinIO — значение по умолчанию Authentik не подходит), кабинет **3020**, BL (FastAPI) **8100**, Nginx gateway **8000**. Топология и хосты — [ADR-0020](0020-local-iam-gateway-topology.md).
  - Nginx локально поднимается нативно для паритета с продом (ADR-0020); кабинет живёт под `basePath: /app`, его BFF — `/app/api/*`.
  - Публично (интернет) агентов не открываем, пока кабинет с входом не работает: иначе расход токенов и утечка ключей.
- **Последствия:**
  - В C4 ([`c4-l1-l2-l3.dsl`](../architecture/c4-l1-l2-l3.dsl)) контейнер `frontend` заменён на `landing` (статика) и `cabinet` (SSR); из Edge убран компонент `jwtCheck`, добавлены `staticServe`, связи `cabinet → iam` (OIDC, обмен кода), `businessLogic → iam` (JWKS) и компонент `businessLogic.authz`. UML ([`uml-component-diagram.puml`](../architecture/uml-component-diagram.puml)) и draw.io приведены к тому же виду.
  - ADR-0015 в части «Frontend» и «Nginx: OIDC / проверка JWT» **уточняется этим ADR** (в таблице стеков дана ссылка).
  - Новый сервис `apps/cabinet` (отдельное приложение, по правилу AGENTS «новый продукт = отдельный сервис в `apps/`»); контракт BL — отдельный OpenAPI (`artifacts/api/`, contract-first): как минимум `/v1/me`, `/v1/agents`, `/v1/runs` и статус запуска (SSE).
  - CI: лендинг остаётся «build → rsync»; кабинет требует отдельной доставки (Node-процесс на целевом сервере). Нагрузка по RAM на сервере — Node кабинета плюс Authentik (Postgres в составе Compose).
  - Нужно обновить копии портфолио (`scripts/export-portfolio.ps1`: `c4.dsl`, `component-diagram.*`, `rag.openapi.yaml`) и пересоздать C4-экспорты в `artifacts/generated`.
  - Подробный план внедрения вытекает из этой архитектуры; ROADMAP ведёт только порядок.
  - Переход на более раннее отсекание неавторизованных запросов (`auth_request` на Nginx) или добавление `operator` как третьей роли — отдельное решение, без смены этого ADR.
